## 2. Where the bake time goes today

The bake (`Nav.BakeStep`, phases floors → edges → components → write) is entirely main-thread Physics: per cell up to 32 downward `Physics.Raycast` hits plus `CheckCapsule` ×2 and one backface ray (`Floor`, Nav.cs:550–605), then per cell 4 neighbour tests each with a `LowWayClear` ray, a top probe and a `CapsuleCast` (`BakeEdges`, :393–433, `BodySweep` :2028). A 0.5 m cell on a 600×600 grid is up to 360k cells × (≈5 casts + 8 edge casts). It is sliced by `BakeBudgetMs` (1 ms/frame, ×0.5 below 45 fps, ×3–4 near the player or when an NPC waits), so a large camp costs seconds-to-minutes of 1–4 ms frames, and the FPS multipliers make it spiky exactly when the player arrives. Reads/writes of `.wwnav` are sliced too; signature mismatch rebakes.

Runtime (`Nav.Next` from `Brain.MoveToward` each think, 0.1 s): Dijkstra field per goal bucket cached `FieldSeconds`, lazy expansion, waypoint = farthest cell in grid sight. That part is cheap; the `OutNext` exit search (`PickJob`, 1 ms/frame, 6000 tests) and the per-think capsule casts in `NavLegClear`/`NavSteer` (5-heading fan) are the runtime cost, not the field.

## 3. Cheaper / decoupled baking (recommendation, in order of payoff)

### 3.1 Batch the physics with RaycastCommand / CapsulecastCommand (jobs, off the main thread)

Unity 2020.3 ships `RaycastCommand`, `SpherecastCommand`, `CapsulecastCommand` and `BoxcastCommand` with `ScheduleBatch` (verified present in the game's `UnityEngine.PhysicsModule.dll`; `NativeArray`/`JobHandle` in CoreModule). These run the casts on the job worker threads and return a `NativeArray<RaycastHit>`; the main thread only fills the command array and reads results. That is the one lever that removes physics work from the frame without changing the bake semantics:

Phase 0 (floors): one `RaycastCommand` per cell (ray from `RefY+6.5` down 14.5 m, `maxHits` 1 → the first hit). Cells whose first hit is not walkable (`normal.y < 0.8`, or above `RefY+6`) get a second batch starting just below that hit (the "up to 32 hits" loop becomes 2–4 batched rounds, almost all cells finish in round 1). `InsideSolid` becomes a batched upward ray with `queryTriggerInteraction` and `Physics.queriesHitBackfaces` set before scheduling. `BodyFits` (two `CheckCapsule`) becomes a `CapsulecastCommand` with distance 0 is not supported, so keep it as one `SpherecastCommand` of radius 0.35 from floor+0.3 up to 1.5 m (hit within distance = blocked); it matches the current clearance within a few cm.

Phase 1 (edges): per cell, 4 neighbours × (`LowWayClear` ankle ray + `BodySweep` capsule cast) → one `RaycastCommand` batch and one `CapsulecastCommand` batch per direction. The "rim ≤ MaxStep, same collider, normal ≥ 0.5" acceptance only needs the hit's `collider`/`normal`/`point`, all in `RaycastHit`.

Batches of 64k commands at `minCommandsPerJob` 256, scheduled in `Tick`, completed one or two frames later (`JobHandle.IsCompleted`, never `Complete()` on the same frame). The main-thread cost per frame becomes filling arrays (≈0.1 ms per 10k commands) and reading results; the whole 360k-cell floor pass finishes in a handful of frames instead of thousands. Note: the existing `Floor` keeps the **lowest** free surface; with batched first-hit rays you get the highest first, so the per-cell loop order must be preserved explicitly (cast from the bottom up: ray from `RefY−8` upward with backfaces off finds the lowest surface facing up).

### 3.2 Move the pure-data phases to a background thread

Phase 2 (connected components), `BuildMasks` (Nav.cs:789), the `Near[]` pass, the FNV hash, the file read/write and the parse of `.wwnav` touch no Unity objects once the hit arrays are copied to managed arrays. Run them on a `ThreadPool` work item (precedent: Towns computes the overlay plan on the MapMagic worker, `TownOverlayPlan`), hand the finished `NavStructure` back through a thread-safe queue consumed in `Tick`. The `MapHash` signature currently reads `Transform`/`Collider` properties — capture those into a plain struct list on the main thread (already done piecewise in `MapHash`, just split capture from hashing). This removes the sliced 0.5 ms `BuildMasks` job and the sliced reader/writer entirely.

### 3.3 Bake once per prefab signature, never per instance (already mostly true)

The template/clone mechanism (`NavMaps`, `TemplateLimit` 96) and the embedded vanilla pack cover the 39 native POIs; what still rebakes is a tilted/mirrored root, an unsupported collider type, or a changed `MaxStep`. Two cheap wins: (a) treat a 90°-multiple yaw and a uniform scale as the same signature with a rotated lookup (today only yaw alignment is kept, see `ConfigureMap` NavMaps.cs:94–131); (b) when a map is missing, bake the **coarse** grid first (cell 1 m, ~4× fewer cells) so the NPC that asked (`_needed`) gets a usable field within a second, then refine to 0.5 m in the background and swap. Towns and gas-station custom maps go through the same path, so they benefit too.

### 3.4 Smaller grids by construction

Margin 4 m around a union-of-bounds footprint means a camp with one far fence post bakes a huge rectangle of empty sand. Bake the **terrain-only** cells (no collider within 1 cell, `Open` sky, slope < limit) at 2 m resolution with a single ray, since terrain is walkable by the feelers anyway, and reserve 0.5 m cells for the band within 3 m of any collider. The current `Near`/`MinArea`/`FloorColCells` logic is unchanged because it only looks at the fine band. Expected: 3–6× fewer physics queries on camps, more on caves (all fine), none on buildings.

### 3.5 Safety margins from walls (Denis's "easier low-cost setup that works well")

The thing NPCs actually bump is not the map, it is the gap between the map's 0.35 m body radius and the feeler capsule (1.15× body extent, up to 0.45 m) plus the 5-heading `NavSteer` fan that ignores `Near`. A distance-to-wall field is the cheap fix: during phase 2, run one more flood fill from every unwalkable cell outward (two BFS passes, 8-neighbour, integer "cells to nearest blocked", stored in one byte per cell — adds 1 byte to the 7-byte cell record, bump `MapVersion` to 2 and the embedded pack is re-exported with the existing Export button). Then: (a) `NearCost` becomes a graded cost (`+3` at 1 cell, `+1` at 2 cells, 0 beyond), so routes hug the middle of corridors without any extra physics; (b) the waypoint pick (Nav.cs:921–937) stops at the first cell whose distance byte ≤ 1 instead of `Near`; (c) `NavSteer` steers toward the waypoint **plus** a small push along the distance gradient when the current cell's byte ≤ 2 — a 2-byte lookup replaces a capsule cast per heading. Also expose `[Nav] WallClearance` (cells, default 1) instead of hardcoding `Near`. This is what makes "cheap pathfinding that works well" without touching the feelers.

## 4. Climbing: higher ground within reach triggers the climb animation

The player already has the whole mechanism: `ClimbGeometry.Find` (face sphere-casts at `MinimumHeight`…`MaximumHeight` 0.45–2.5 m, 5 top rays, capsule clearance) and `ClimbPath.At` (lift then move forward, 0.6/0.72 split) with clips `ClimbWaist`/`ClimbHigh` from `apocaplayer_climbing.bundle`. NPCs get the same in three parts, none of which needs a new physics system:

Bake: today a cell keeps only the lowest floor and a neighbour with `dy > HopStep` (0.5) is a wall. Add a third edge kind, **climb edge** (two spare bits are left in the edge byte, Nav.cs:405–428: walk 0–3, hop 4–5 → climb 6–7 for the two straight axes; diagonal climbs are never needed; the edge is stored on the lower cell and the up/down direction follows from the two floor heights, a downward traversal being a drop, which `DropCheck` already allows up to 4 m). A climb edge from cell A to neighbour B exists when `0.5 < B.y − A.y ≤ ClimbMax` (default 2.2 m, under the player's 2.5), the face between them is near-vertical (`BodySweep` from A at A.y+0.3 hits a collider whose normal has `|y| < 0.35` — one capsule cast, already done for the hop test, just keep the hit), and B's floor has standing clearance (B is walkable, and a `BodySweep` at B.y toward the far side is clear). Upper floors: when the floor scan finds a second walkable surface more than 2.2 m above the lowest it is still dropped (one floor per cell stays, so no save-format change beyond the edge bits) — roofs reached by climbing therefore need their own cells, which they have whenever the roof is inside the prefab footprint and the ray from `RefY+6.5` sees it first; so the second-pass rule in 3.1 (lowest surface) must also record the **highest** walkable surface ≤ `RefY+6` as a separate "upper" cell layer only where a climb edge or ladder leads to it. Keep that layer optional (`[Nav] UpperFloors`, default on) and bump `MapVersion`.

Route: Dijkstra gets `ClimbCost` (+6, so a climb is taken only when the walk-around is more than ~3 m longer, tunable) and the route field expands over climb edges only for humans (`a.Cone == 0`, not dogs/insects — give them `_noClimb` like `_noHop`). The waypoint stops **at** the climb cell with a flag "climb next", exactly as hop cells do.

Execution: `Brain.TryHop` is the template. A new `TryClimb` (Brain.cs beside `TryHop` :1571) fires once per climb edge: it runs `ClimbGeometry.Find` with the NPC's forward (make `Find` a Core service call `Services.Animation.FindClimb(origin, forward, minH, maxH)` so the NPC module never references PlayerBody types — same rule as every cross-module call), and on success starts a per-NPC traversal: Rigidbody kinematic, `body.position` driven by `ClimbPath.At` in `FixedUpdate` through the brain's existing per-body component, feelers/senses paused, done at 65 %. Animation: `IAnimatedCharacter` has no "play clip" entry today. Add one member, `Traversal(AnimationClip clip, float speed)`, implemented in `ModCharacter` with the same `AnimationMixerPlayable` lease that `PlayerTraversal.Body.BeginTraversal` uses (PlayerTraversal.cs:72), and expose the two climb clips through `IAnimationApi.GetClip("ClimbWaist"/"ClimbHigh")` by also loading the climbing bundle in `Anims` (it is already on disk). NPCs running the native controller (ApocaplayerClips off) fall back to a Rider-style temporary `PlayableGraph` on their humanoid Animator (precedent `Rider.JumpClip`, Patrols/Crews/Rider.cs:969), destroyed when the climb ends. Starting camp acceptance: a guard chasing the player onto the container stack climbs the 1.2–2 m lips instead of circling; a lip over 2.2 m is routed around.

Cost: one extra capsule hit kept per neighbour during the bake (no new casts), one `ClimbGeometry.Find` per climb (≈10 casts, at most once per NPC per 2 s), zero per-frame cost otherwise.

## 5. Ladders (Buzzgut's fortress, town small towers)

Native ladders are a `ladder_trigger` child, tag `Ladder`, layer 2 (Ignore Raycast), trigger BoxCollider — the player's `UseLadder` FSM reacts to entering it (Patrols/WarRig/Props.cs:140–172 recreates one for the War Rig, Towns copies `decor/ladder_L`). Layer 2 is excluded from `BakeMask`, so today ladders are invisible to the bake, which is exactly what we want for walkability and exactly what makes them easy to find as links.

Bake: in `Make`, enumerate trigger colliders with tag `Ladder` under the root (there are a handful per prefab, so `GetComponentsInChildren` once per bake is fine). For each, the bottom link cell is the walkable cell at the trigger's `bounds.min.y` on the side the ladder faces (ladder forward = the trigger's local −Z/+Z, pick the side whose cell is walkable), the top link cell is the walkable cell at `bounds.max.y` on the opposite side (the platform). Both must resolve to cells (the top needs the upper-floor layer from section 4; towers put the platform well above `RefY+6`, so extend the floor scan window to the ladder top for those columns only). Store ladders as a small list in the map (`count`, then bottom cell, top cell, world-relative bottom/top points, facing yaw; versioned, so `MapVersion` 2 covers 3.5/4/5 together). Each ladder adds two directed "ladder edges" into the Dijkstra graph with `LadderCost` = height × 2.

Execution: a ladder climb is a scripted traversal like section 4, not physics: walk to the bottom point (the usual waypoint, arrive radius 0.4 m, face the ladder), then kinematic move up the ladder line at `LadderSpeed` (1.2 m/s) with a looping climb clip, then a 0.6 m forward step onto the top cell; descending reversed. Use the native `UseLadder` FSM? No: it drives the player's controller and camera; NPCs don't have it. Only humans use ladders (`_noClimb` group rule). One NPC per ladder at a time (a per-ladder "busy" flag in the live structure; the second waits at the bottom via the existing `Wait`/`Rest`). Combat rule: an NPC on a ladder has `Senses` paused (like `Travel` for burrowers) and takes damage normally; killed on a ladder → the corpse falls (restore non-kinematic before `_Dead` swap).

Buzzgut acceptance: a camp guard alerted on the ground reaches the walkway behind the player via the ladder; a sniper on the tower comes down the ladder when the player is below and unseen for `LoseSeconds`; two guards do not stack on one ladder.

## 6. Secondary feature: NPCs take a car and ram the player

What exists: `Patrol.SeatLiveDriver` (seat a prefab copy, `Crew.Attach`, `Pilot.Attach`), `Pilot.StepCharge` with the `ramming` flag (`AiRamDistance`, `RamTargets`), `Ram.Sensor` for damage, `CrewReturn` for walk-to-door and `Seat()` (walks via `Services.Npc.Travel`, destroys the walking body, seats a copy), `CrewReturn.Unusable` for the usability list, and `InputControl.Take/Release` for stealing the car's INPUT FSMs. There is **no** hijack code and no wheel/steering check (`hinge_wheel_*` is used only for geometry, `hinge_steeringwheel` only in the hinge list).

Design (Patrols module, new file `Crews/Hijack.cs`, plus one NPC service member):

Trigger: a hostile human NPC in `Combat` with the player (or holding a fought-memory), on foot, that is `HijackMinDistance` (25 m) or more from the player, and a car within `HijackSearchRange` (40 m) of the NPC that passes `Usable`: not the player's car (`PlayerRef.PlayerCar`), not `marker.PlayerEntered` in the last 10 s, no living crew, `hinge_engine` with a child, fuel > 0.01, four `hinge_wheel_*` hinges each with a child wheel (the "4 wheels" rule — bikes and 3-wheelers excluded), a `hinge_steeringwheel` with a child, `up.y ≥ 0.35`, not `Explode.IsWreck`, not `StuckBails > 0`. The player's own parked car qualifies when the player is out of it — that is the point of the feature. Cooldown per car (60 s) and per NPC (30 s) after a failed attempt.

Boarding: `Services.Npc.CrewOrder(npc, player, boarding: true)` already suspends the brain's combat for boarding; order the walk with `Services.Npc.Travel(body, BoardPoint(driver seat), 2.75)` exactly as `CrewReturn.Order`; on arrival `OpenDoorAt`, then `Seat()` pattern: `SeatLiveDriver` with the NPC's prefab name and current health, `Register.RemoveTree`+destroy the walker, `Crew.Attach`, `Patrol.Handbrake(false)`, `Patrol.StartUp`, `InputControl.Take`, `Pilot.Attach`. The seat copy needs the crew tags/identity carried over (health, WoW appearance via `Services.NpcAppearance`, the Scrapyard/Coyotes tag) — the same transfer `CrewReturn.Seat` does.

Driving: Pilot needs a target without a `PatrolMarker` journey. Give the hijacked car a lightweight `PatrolMarker` with `Rams = RamTargets.Pedestrians|Cars` and the NPC's faction (so `Ram.Sensor` and `TrafficFactions.DriveTarget` work unchanged), `SetupOnly`-style so Persistence does not save it as a patrol (or mark it `Hijacked` and strip the marker on exit). `Pilot` then charges/overshoots/turns exactly like a raider car. Exit rules: `Unusable` (stuck, flipped, out of fuel) or the player dead/unseen for `FoughtMemorySeconds` → `Crew.ExitCrew` (existing bail: the NPC is back on foot and the car is left with `StuckBails` untouched so another NPC may try later). Player re-enters the car while the NPC walks to it → cancel (`marker.PlayerEntered`).

Saves: a hijacked car mid-drive is just a car with a seated live driver; `Crew` already restores drivers through `PrepareLoaded` and the Patrols ES3 keys, but the marker must be flagged so a reload does not turn the player's own car into a permanent patrol — simplest is to always bail out on `OnSaveBegin` for hijacked cars (they are never saved as driven), noted as a limit.

Settings: `[Patrols / Hijack] Enabled` (default on), `MinDistance` 25, `SearchRange` 40, `Cooldown` 60; Debug `HijackLog`. Scope: Patrols only, plus the one NPC service call it already has (`CrewOrder`, `Travel`). Build after the pathfinding work because the walk-to-door path must cross camps reliably (section 3.5) and because the car near the starting camp is usually the player's own parked car, which this feature makes dangerous by design.
